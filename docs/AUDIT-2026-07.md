# Kino — Audit técnico · Julio 2026

> Audit read-only (sin fixes). Severidades: **Critical** (data loss / security / roto en prod) · **High** (bug que afecta uso real) · **Medium** (deuda, UX pobre) · **Low** (nitpick). Los hallazgos marcados *(sospecha)* requieren verificación antes de tratarlos como bug confirmado.

## Resumen ejecutivo

Estado general: **sólido para un producto de una persona**. `tsc --noEmit` pasa limpio, 178/179 tests pasan, la autorización por `userId` está presente en prácticamente todas las queries, y la validación Zod cubre casi todos los endpoints. No se encontró ningún hallazgo Critical (no hay data loss ni fuga de datos entre usuarios explotable de forma directa). La deuda se concentra en: (1) el pipeline de migraciones Drizzle está desincronizado del journal, lo que hace peligroso cualquier `drizzle-kit generate` futuro; (2) huecos de validación de ownership en referencias secundarias (`parentTaskId`, `contextTagId`, `systemId` de time logs, `parentPageId`); (3) un bug real de React hooks en el calendario global que puede crashear la vista; (4) el indicador de salud de sistemas lee una tabla que nada escribe (feature fantasma que muestra información incorrecta); y (5) un off-by-timezone en el conteo de energía diaria. Los 5 más graves: **DB-01, FE-01, DB-04, BE-01, BE-05**.

## 1. Base de datos / Drizzle

### DB-01 · High · Journal de migraciones desincronizado
`drizzle/meta/_journal.json` solo registra 2 entradas (`0000_nice_eternity`, `0001_black_prodigy`), pero el directorio `drizzle/` contiene 10+ archivos SQL (`0001_task_type_enum.sql` … `0009_project_systemtype.sql`, `backfill_project_tags.sql`). Además hay **dos archivos con índice 0001**. Las migraciones 0002–0009 se aplicaron por fuera del journal (db:push o psql manual). Consecuencia: `drizzle-kit generate` diffea contra el snapshot 0001 y produciría una migración divergente/destructiva; `drizzle-kit migrate` en una DB nueva no reproduce el schema real.
Posible fix: regenerar snapshot baseline y re-inicializar el journal.

### DB-02 · Medium · `tasks.status` es varchar, no el enum, y su default contradice al código
`taskStatusEnum` está definido en `src/shared/db/schema.ts:75-82` pero `tasks.status` es `varchar(50)` con `default('today')` (`schema.ts:622`). No hay constraint a nivel DB (cualquier string entra por SQL directo/bug), y el default `'today'` contradice el default real del servicio (`'backlog'`, `tasks.service.ts:330`). Mismo caso `boardStatus` (`schema.ts:626`) sin FK/check contra `system_status_definitions`.
Posible fix: CHECK constraint o migrar a enum; alinear el default.

### DB-03 · Medium · Tablas muertas: gamificación y sync
`quests`, `inventory_items`, `energy_logs`, `sync_connections` (`schema.ts:1007`, `1036`, `984`, `1056`) no tienen ni una referencia fuera de `schema.ts` (grep en `src/` y `packages/`). `default_context_tags` (`schema.ts:1128`) tampoco *(sospecha: podría sembrarse desde `init-db/`)*. `users.xpTotal`/`users.coins` se escriben (`tasks.service.ts:142-147`) pero **jamás se muestran en UI** (grep de `xpTotal|coins|xp_earned` en `.tsx`: cero resultados de display).
Posible fix: decidir si la gamificación va o se elimina (pregunta de producto, ver §7).

### DB-04 · High · `system_health` nunca se escribe → indicador de salud siempre vacío
`getSystemHealthIndicator` (`systems.service.ts:133-161`) lee `system_health`, pero **ningún código inserta o actualiza esa tabla** (grep de `insert(systemHealth)`/`update(systemHealth)`: cero). Resultado: siempre retorna `daysSinceActivity: null` y `stale` depende solo de `expectedFrequency === 'daily'`. La ruta `/api/systems/[id]/health` y el tool MCP `find_stale_systems` reportan datos falsos. Feature fantasma con UI visible.
Posible fix: escribir system_health al completar tareas / log de tiempo, o quitar el indicador.

### DB-05 · Medium · Columnas muertas en `user_settings` y FK diferida sin aplicar
`brainDumpDefaultSystem`, `peakEnergyStart`, `peakEnergyEnd` (`schema.ts:246-251`) no se referencian fuera del schema. El comentario en `schema.ts:270-276` documenta una FK (`fk_settings_braindump`) que debía aplicarse por migración raw — no existe ningún SQL en `drizzle/` que la cree *(sospecha: verificar en la DB real)*.
Posible fix: dropear columnas muertas o conectar la feature.

### DB-06 · Low · Enums legacy arrastrados
`taskTypeEnum` conserva `habit|todo|project` como legacy (`schema.ts:114-125`) y `syncProviderEnum` tiene 7 valores para una feature inexistente (`schema.ts:145-155`). `users.provider/providerId` (`schema.ts:214-215`) duplican lo que Better Auth guarda en `accounts`.
Posible fix: limpieza cuando haya ventana de migración.

## 2. Backend

### BE-01 · High · Off-by-timezone en el presupuesto de energía diario
`tasks.service.ts:73`: `${tasks.completedAt} >= (NOW() AT TIME ZONE ${tz})::date::timestamptz`. El cast `::date::timestamptz` interpreta esa medianoche **en la timezone del servidor (UTC en Vercel)**, no en la del usuario. Para `America/Santo_Domingo` (UTC-4) el "día" de energía empieza a las 20:00 del día anterior local: tareas completadas entre 20:00 y 00:00 de ayer cuentan contra el límite de hoy. Contrasta con el patrón correcto usado en `ensureTodayPlanRolled` (`tasks.service.ts:671`: `start_date AT TIME ZONE tz)::date = today`).
Posible fix: `((NOW() AT TIME ZONE tz)::date::timestamp AT TIME ZONE tz)` o comparar días con `AT TIME ZONE`.

### BE-02 · High · Estado `archived` sin transiciones + dos modelos de borrado inconsistentes
`TRANSITION_MAP.archived = {}` (`tasks.state-machine.ts:60`) → el test `archived + soft_delete => archived` falla (única falla de la suite, `tasks.state-machine.test.ts:51`). Además coexisten dos semánticas de borrado: la state machine trata `soft_delete` como `status='archived'` + `deletedAt` (`tasks.state-machine.ts:115-119`), pero `deleteTask` (`tasks.service.ts:468-477`) — el que usa la ruta DELETE real — solo setea `deletedAt` sin tocar `status` ni pasar por la máquina. `restoreTask` (`:479`) devuelve la tarea con su status anterior sin reconciliar. La máquina de soft_delete es efectivamente código muerto en el flujo real.
Posible fix: decidir un único modelo (archived vs deletedAt) y alinear máquina, servicio y test.

### BE-03 · High · Huecos de ownership en referencias secundarias
Todas las queries principales filtran por `userId`, pero varias referencias anidadas no se validan:
- `updateTask` acepta `parentTaskId` (`tasks.schemas.ts:64`) y lo persiste **sin validar** existencia/ownership/ciclos (`tasks.service.ts:361-466` — solo valida systemId, folderId, sprintId). Una tarea puede quedar como padre de sí misma o hija de una tarea de otro usuario.
- `createTask`/`updateTask` no validan que `contextTagId` pertenezca al usuario (FK solo exige que exista).
- `createTimeLog` (`tasks.service.ts:826-848`) inserta `data.systemId` del body sin verificar que pertenezca al usuario ni que coincida con `task.systemId` → time logs con systemId ajeno/incoherente, que luego contaminan agregados por sistema (`idx_timelogs_system`).
- `createPage` valida `folderId` pero no `parentPageId` (`pages.service.ts:188-210`).
Posible fix: validar ownership de cada FK entrante + check anti-ciclo en parentTaskId.

### BE-04 · Medium · Writes múltiples sin transacción
- `createTask` (`tasks.service.ts:270-359`): insert de task + `syncAutoReminders` + insert de reminder tipo `reminder` — tres writes sin tx; un fallo intermedio deja tareas sin reminders (o viceversa).
- `syncAutoReminders`/`clearAutoReminders` (`:180-209`) usan `db` global, nunca la tx del caller.
- `bulkCreateTasks` (`:784-790`) es `Promise.all(createTask)` — sin tx, sin atomicidad; una falla parcial crea un subconjunto sin reporte de cuáles fallaron.
Posible fix: envolver en `db.transaction` y pasar `tx` a los helpers.

### BE-05 · Medium · Notificaciones se marcan como enviadas aunque el push falle
`sendStandardReminders` (`notifications.service.ts:67-100`): los pushes van en `Promise.allSettled` (los rechazos se ignoran) y luego `markTasksNotifiedDueDay/BeforeDay` marca **todas** las tareas como notificadas. Un fallo transitorio de web-push pierde la notificación para siempre. Igual patrón en `sendPendingReminders` (`:109-119`).
Posible fix: marcar solo las de usuarios cuyo envío resolvió.

### BE-06 · Medium · Recordatorios con hora exacta que solo disparan 1×/día
`vercel.json` corre `/api/cron/task-reminders` a las 13:00 UTC (9:00 en Santo Domingo). `task_reminders.remind_at` es un timestamp exacto (el usuario puede crear "recuérdame a las 17:00"), pero se procesa una vez al día: cualquier reminder con hora posterior a las 9am local llega al día siguiente. El tipo de tarea `reminder` (que crea un reminder en el `dueDate` exacto, `tasks.service.ts:348-356`) sufre lo mismo.
Posible fix: aumentar frecuencia del cron o comunicar la limitación en la UI (ver §7).

### BE-07 · Medium · Dos idiomas de auth conviviendo: rutas invisibles para MCP/API keys
`getAuthContext` (cookie + API key + OAuth) vs `auth.api.getSession` (solo cookie). Usan session-only: `/api/tasks/today-plan`, `/api/energy/advisor`, `/api/users/setup`, `/api/push/*`, `/api/connect/cli`, y los server actions (`tasks.actions.ts:8`). Hoy ningún tool MCP apunta a esas rutas (el `get_today_plan` del MCP usa `/api/energy/plan/today`, que sí usa `getAuthContext` — `energy.routes.ts:12`), pero es una trampa recurrente ya documentada: el próximo tool que toque una ruta session-only fallará silenciosamente con 401.
Posible fix: estandarizar en `getAuthContext` salvo rutas intrínsecamente de navegador (push).

### BE-08 · Medium · Manejo de errores inconsistente entre rutas
`listTasks` (`tasks.routes.ts:47-66`) y `getSubtasksRoute` (`:247-257`) no tienen try/catch (un throw → 500 sin formato JSON estándar), mientras el resto de handlers del mismo archivo mapean NotFound/Validation con cuidado. `GET /api/systems/[id]/tasks` (`tasks.routes.ts:24`) traga cualquier error con un catch genérico que oculta la causa.
Posible fix: wrapper compartido de handler con mapeo de errores.

### BE-09 · Low · `CRON_SECRET` sin guard de existencia *(sospecha)*
`api/cron/task-reminders/route.ts:7`: si `CRON_SECRET` no está definido en el env, el header literal `Bearer undefined` autentica. Verificar que el env existe en prod.
Posible fix: `if (!process.env.CRON_SECRET) return 500` antes de comparar.

### BE-10 · Low · Reorders en loop de N updates
`reorderTasks` (`tasks.service.ts:508-517`) y `reorderSystem` (`systems.service.ts:163-176`) hacen hasta 50 UPDATEs secuenciales por request. Con Neon serverless cada round-trip cuesta.
Posible fix: un solo UPDATE con `CASE`/`unnest`.

### BE-11 · Low · MCP hace loopback HTTP contra sí mismo
`api/mcp/route.ts:17-28`: cada tool call re-entra por HTTP al propio deployment (`createKinoFetch({ baseUrl: APP_URL })`) y re-valida el token en `getAuthContext`. Doble latencia y doble verificación JWT por tool call. Diseño consciente (aísla por REST), pero costará cuando haya tools compuestos.
Posible fix (futuro): capa de servicio compartida en vez de self-fetch.

### BE-12 · Low · Rate limiting in-memory y solo en `/api/auth`
`src/proxy.ts:9-48`: limitador en Map por instancia (trade-off documentado en el propio archivo) y ningún rate limit en el resto de la API (p. ej. bulk create de 50 tareas sin límite de frecuencia).

## 3. Frontend

### FE-01 · High · Hook condicional en el calendario global (crash potencial)
`GlobalCalendarView.tsx:154` hace `if (!d) return null;` **antes** de `useDraggable` en `:161` (error `react-hooks/rules-of-hooks` confirmado por el linter). Si el `placementDate` de una tarea pasa de válido a null entre renders (p. ej. autosave limpia la fecha mientras el calendario está montado), React lanza "Rendered fewer hooks than expected" y la vista entera crashea — y no hay `error.tsx` que lo contenga (ver FE-03).
Posible fix: mover el early-return después del hook o extraer subcomponente.

### FE-02 · Medium · Sin error boundaries ni loading en rutas principales
No existe **ningún** `error.tsx` ni `not-found.tsx` en `src/app/` (find confirmado). `loading.tsx` solo existe para dashboard, systems/[id], folder y page — faltan `/tasks`, `/calendar`, `/settings`, `/systems`. Un throw en server component = pantalla de error genérica de Next.
Posible fix: `error.tsx` global + loading en las 4 rutas.

### FE-03 · Medium · Derivación optimista de status duplicada y en timezone del navegador
`useCreateTask` (`tasks.hooks.ts:93-106`) replica a mano `deriveStatusFromDate` usando la tz del navegador, mientras el backend usa `users.timezone` (`tasks.service.ts:329`). Si difieren (viaje, tz mal configurada), la tarea aparece en "Hoy" y tras el refetch salta a "Mañana" sin explicación.
Posible fix: extraer la derivación a un helper compartido que reciba tz.

### FE-04 · Medium · setState síncrono en efectos (lint errors)
`AuthForm.tsx:48` (`setCoach` en useEffect para evitar hydration mismatch) y `HeroDemo.tsx:50` (`setMounted(true)`) — ambos flaggeados por el linter (`react-hooks/set-state-in-effect`). Cascading renders; el patrón correcto es `useSyncExternalStore` o inicialización lazy.

### FE-05 · Medium · Archivos monolíticos en la feature tasks
`tasks.hooks.ts` (872 líneas — todos los hooks de la feature en un archivo), `CreateTaskDialog.tsx` (556), `TaskDetailSheet.tsx` (553), `GlobalCalendarView.tsx` (649). No es bug, pero cada cambio toca un archivo gigante y el `form.watch` de CreateTaskDialog ya desactiva el React Compiler para todo el componente (warning `react-hooks/incompatible-library`, `CreateTaskDialog.tsx:143`).
Posible fix: partir por vista/preocupación cuando se toquen.

### FE-06 · Low · `dueDateHasTime` no aplica la heurística de medianoche UTC
`tasks.utils.ts:85-88` usa `getHours()` local puro, mientras `parseTaskDay` (`:71-82`) tiene una heurística explícita para datos importados a medianoche UTC (MCP/seeds). Una tarea importada con `2026-07-10T00:00:00Z` en UTC-4 muestra hora "20:00" espuria del día anterior en la UI. *(sospecha: depende de cuántos datos entren por MCP con día pelado)*.
Posible fix: reusar la misma heurística en ambas funciones.

### FE-07 · Low · `dueBeforeStart` compara días con slice lexicográfico
`tasks.schemas.ts:17-19` compara `dueDate.slice(0,10) < startDate.slice(0,10)` sobre strings que pueden ser ISO **en UTC** generados por `dayToLocalISO` (que corre el día en tz negativas: `2026-07-03 20:00-04` serializa como `2026-07-04T00:00Z`). La validación puede aceptar/rechazar incorrectamente en bordes de día.
Posible fix: comparar con `parseTaskDay` en ambos lados.

## 4. UI/UX y flujo de usuario

### UX-01 · High · Indicador de salud de sistemas miente (feature fantasma)
Consecuencia visible de DB-04: cualquier UI que pinte "stale"/salud de un sistema muestra datos que no se calculan desde actividad real. Para un usuario nuevo, todos los sistemas `daily` aparecen stale desde el día 1.

### UX-02 · Medium · Gamificación invisible
Completar tareas otorga XP en DB (`tasks.service.ts:142-147`) y el endpoint devuelve `xp_earned`, pero ninguna vista lo muestra (grep en `.tsx`: solo la declaración del tipo en `tasks.hooks.ts:15`). El usuario acumula un contador que no existe para él. Junto con las tablas muertas de DB-03, la gamificación es un sistema a medio enterrar.

### UX-03 · Medium · El límite de energía bloquea planificar según lo ya **completado**
`validateTransition` (`tasks.state-machine.ts:73-81`) rechaza `move_to_today` cuando `energía_completada_hoy + tarea > límite`. Semántica cuestionable: mientras más productivo fue tu día, menos puedes planificar para lo que queda de él; al final del día es imposible añadir nada a Hoy y el error ("Límite de energía diario excedido") no ofrece override. Fricción real en el flujo principal de planificación. (Además el conteo sufre BE-01.)

### UX-04 · Medium · Recordatorios: la UI promete hora exacta que el sistema no cumple
El usuario puede fijar `remindAt` con hora (`TaskRemindersSection.tsx`, tipo `reminder` con TimePicker del último commit), pero BE-06 implica que llegan en el batch de las 9am local. Expectativa rota sin aviso en la UI.

### UX-05 · Low · Sin `not-found.tsx`
Navegar a un sistema/página/folder inexistente (link viejo, otro dispositivo) cae en el 404 crudo de Next en vez de un dead-end amable con vuelta al dashboard.

*(Nota: el recorrido mobile [ResponsiveDialog, vistas `*MobileView`, sin DnD táctil] sigue las convenciones documentadas; no encontré divergencias nuevas evidenciables por código estático. Un pase manual en dispositivo sigue pendiente como verificación.)*

## 6. Decisiones técnicas cuestionables / deuda arquitectural

### AR-01 · Medium · Convención de rutas API duplicada
Conviven dos patrones: rutas thin que re-exportan de `*.routes.ts` del feature (`api/tasks/route.ts`) y rutas con lógica inline (`api/tasks/today-plan/route.ts`, `api/pages/[id]/subpages/route.ts`, todos los `api/cron/*`). El mismo árbol tiene 3 estilos de auth, 2 de validación y 2 de manejo de errores. Cada endpoint nuevo elige al azar.

### AR-02 · Medium · Lógica de "hoy" en 4 implementaciones distintas
El cálculo del día del usuario existe como: `calendarDateInTz` (`tasks.utils.ts:9`), `getTodayDate` (`energy.service.ts:54`), SQL `(NOW() AT TIME ZONE tz)::date` (`tasks.service.ts:633`), y la versión rota `::date::timestamptz` (BE-01). Cuatro sitios que pueden divergir — de hecho ya divergieron (BE-01, BG-04).
Posible fix: un módulo `shared/time` único (TS + fragmento SQL).

### AR-03 · Low · Doble lockfile commiteado
`package-lock.json` y `pnpm-lock.yaml` ambos trackeados en git (`git ls-files` los muestra); el workspace es pnpm (`pnpm-workspace.yaml`). npm install accidental produce un lockfile divergente.
Posible fix: borrar package-lock.json y añadirlo a .gitignore.

### AR-04 · Low · `deriveAction` duplica el TRANSITION_MAP
`tasks.service.ts:152-173` re-declara a mano las 17 aristas que ya existen en `TRANSITION_MAP` (`tasks.state-machine.ts:27-61`). Ya están desincronizados: `deriveAction` no tiene ninguna arista hacia `archived` ni desde ella, así que `moveTask`/`bulkMoveTasks` con `status: 'archived'` (que el schema Zod permite, `tasks.schemas.ts:96-99`, y el tool MCP `bulk_move_tasks` expone) siempre falla con 422.

### AR-05 · Low · Naming
`getSystembyId` (minúscula, `systems.service.ts`), `api_keys` en snake_case cuando el resto del schema usa camelCase (`schema.ts:1212`), package name `nextjs-vertical-slice-app` en `package.json:2`.

## 7. Preguntas abiertas (decisión de producto)

1. **Gamificación (XP/coins/quests/inventory)**: ¿se construye la UI o se elimina el subsistema completo (DB-03, UX-02)? Hoy es peso muerto que además ejecuta writes en cada toggle.
2. **Semántica del límite de energía** (UX-03): ¿el límite debe contar energía *completada* (como hoy), energía *planificada en Hoy*, o ambas? Cambia la state machine y el copy del error.
3. **Modelo de borrado** (BE-02): ¿`archived` es un estado terminal navegable distinto de la papelera (`deletedAt`)? Hoy el código implementa ambos a medias.
4. **Recordatorios con hora exacta** (BE-06/UX-04): ¿subir la frecuencia del cron (costo en Vercel free) o degradar la promesa de la UI a "el día de"?
5. **Indicador de salud de sistemas** (DB-04): ¿reconstruir el pipeline de `system_health` o retirar el indicador hasta que exista?
6. **`user_settings` muertos** (DB-05): ¿`peakEnergy*`/`brainDumpDefaultSystem` son roadmap o se dropean?
